# Provider 请求策略（每分钟请求数 + 并发上限）

- 主责包：`apps/zcode-cli/packages/bootstrap`
- 涉及其它包：`packages/provider`（配置 schema 与解析）、`apps/zcode-cli/packages/contracts`（`ModelRequestAdmission` 端口）、`apps/zcode-cli/packages/core`（子会话继承端口）、`apps/zcode-cli/packages/adapters`（runner 的 `admitAttempt`）、`apps/zcode-cli/packages/dynamic-workflow`（AIMD 控制器）

## 背景与问题

服务商侧的节奏约束长在**账号**上，不区分这次请求来自主代理、子代理还是工作流。ZCode 侧唯一读得到策略数字的地方是已解析的 Provider Registry（`ProviderConfig.requestPolicy`），用户面入口是设置 → 模型设置 → 服务商卡片 → 「请求策略」。两个旋钮对应两种真实约束：

- `requestsPerMinute`：每分钟最多 N 次。按它限速后突发被压平。
- `maxConcurrent`：同时最多 N 个在飞。有的服务商**只限并发不限次数**，且超发时不返回 429 而是静默排队——AIMD 学不到墙在哪里，只能靠这条声明硬性卡住。

第二轮约束下「按胜率限速后并发自然被压住」不成立：长时间流（一次 60 秒）会把平均在飞数顶到 `RPM × 时长 / 60`。本地若没有并发闸门，请求就只能堆进上游队列、等到超时、再重试——重试重新占位，最终大家一起失败。

模型请求有许多条发出路径，各自构造自己的 runtime。只要有一部分路径没拿到策略端口，它们就会在主代理看不见的地方把配额吃光。本轮之前有两条这样的路径：

1. legacy `Workflow` 工具的子代理（`script-workflow-runtime.ts` → `createScriptWorkflowAgentRuntime`）；
2. expert workflow facade 的 workflow 子 runtime（`workflow-facade.ts` 的 `createWorkflowChildRuntime`）。

两者曾因为「不参与进程级并发治理」而拿一张「只限速、并发直通」的票。那个旁路对并发的 `maxConcurrent` 同样不成立——它们发的是同一个 provider 的请求，provider 的并发墙一样会被它们撞。本轮把它们收编到主代理同款的准入端口。

## 设计决策

- **限速是端口上的装饰层**：`withProviderRateLimit(inner, port)` 只在既有并发闸门上补一个 `awaitRateLimit`。谁拿到端口谁受限，所以覆盖面等于端口的装配范围，而不是散落在各发送点。新增调用路径时，问题从「记得加限速」变成「记得带端口」。
- **进程级单例、按 `providerId` 分桶**（`getProviderRateLimiter`）：一条 provider 配置 = 一份策略 = 一个桶。同一进程里的多个会话（app）共用一份桶；Windows 桌面与 WSL 远端同名即共享。每次请求重读配置，设置页改完立即生效，不重建桶。
- **令牌桶而非滑动窗口**：桶是三个标量，不随在飞量增长。代价是突发边界上略有出入（满桶可 N 连发，随后匀速补），对配额约束而言这正是想要的语义——用户配的是**节奏**。
- **并发是两层、两个粒度**（`workflow-concurrency-governor`）：
  - **AIMD 桶**按 `${providerId}/${modelId}` 分：429 / Retry-After 是「学习」信号，按模型来（不少服务商按模型分层配额）。cap 的爬升、冷却、空闲重置都长在桶上。
  - **provider 闸门**按 `providerId` 一道：`maxConcurrent` 是**声明**的上游硬上限，必须跨模型桶结算在飞总和。分开数的话每个模型各到 N 个，合起来照样撞墙。
  - 未配置 `maxConcurrent` 时 provider 闸门不存在，行为与从前逐字相同。
- **同机多端共享同一份并发额度**（`provider-concurrency-shared`）：`maxConcurrent` 声明的是**上游**的墙，
  两端各限 N 就是 2N。所以本进程可用额度改成 `N − 另一进程广告的在飞数`。这是「广告 + 收敛」，不是
  分布式信号量——无锁、无租约，也就没有崩溃后永久泄漏的槽位（详见「跨进程共享」）。
- **主代理（observer）在配置了上限的 provider 上守 provider 总量、走优先通道**：模型的 AIMD cap 与冷却不拦它（用户交互永不被 workflow 流量阻塞），放行次序先于任何 run 的等待者。未配置时维持无条件放行、只喂信号。
- **一站式准入端口**：主代理、workflow run 与 legacy 子代理拿到的是同一个装饰后的 observer 端口。不再提供「只带配额、并发直通」的准入实现。

## 行为

受限的调用路径（共用同一份 per-provider 策略）：

| 路径                                                | 端口来源                                                                  |
| --------------------------------------------------- | ------------------------------------------------------------------------- |
| 主代理（turn step、工具内部调用、sidecar）          | `create-app`：`withProviderRateLimit(governor.observer(), port)`          |
| Agent/Task 工具派发的子代理（前台 / 后台 / 冷恢复） | 继承父 runtime 的端口（`core/src/runtime/methods/subagent.ts`）           |
| 动态工作流（dwf）的每个 actor                       | driver 的 per-actor 准入端口（AIMD 桶 + provider 闸门），座位闸门透传     |
| legacy `Workflow` 工具的子代理                      | 本轮起：与主代理同一个装饰端口的 observer（RPM + provider 并发闸门都生效） |
| expert workflow facade 的子 runtime                 | 本轮起：同上                                                              |
| 辅助对话（`selection_side_chat`）                   | 普通会话 fork 路径，走标准会话构造，天然带端口                            |
| 标题生成 / 压缩摘要 / 记忆提取 / 目标校验           | 统一走 `createRuntimeModel`，准入端口在句柄工厂绑一次                     |

不受限：

- **非模型请求**：拉取模型列表、插件市场、MCP OAuth、provider 连通性探测。它们不消耗 LLM 配额。
- **不在同一台机器上的进程**：不做任何跨进程协调（每个进程各按自己的配置卡）。同机多端（Windows 桌面 + WSL 远端）则**两样都共享**：RPM 余额落在同一个文件、并发在飞数落在同一个目录，见下一节。

## 跨进程共享（同机多端：Windows 桌面 + WSL 远端）

两台进程的**数据根隔离**，但摸得到**同一块磁盘**（Windows `%ProgramData%` ↔ WSL `/mnt/c/...`）。两个约束的物理性质不同，所以共享机制也不同：RPM 用「一个文件 + 文件锁」，并发用「一人一份报告 + 收敛」。

### RPM 余额：一个文件 + 文件锁

进程内的桶只能管住自己这个进程，于是「Windows 限 20/min、WSL 限 20/min」合起来能到 40/min。所以把桶的余额落到一个共享文件，每次请求在文件锁下「读 → 补 → 扣 → 写」。

- **位置**（两端必须算到同一个文件，所以锚点是「这台机器的系统盘」而不是各自的数据根）：
  - Windows：`%ProgramData%\zcode\provider-quota.json`
  - WSL：`/mnt/c/ProgramData/zcode/provider-quota.json`（默认挂载下与上面是同一个文件）
  - 覆盖开关：`ZCODE_PROVIDER_QUOTA_SHARED_FILE`（绝对路径；写成 `off` / `0` / `false` / `none` 则显式关闭共享）
  - 读不到锚点（非 Windows / 非 WSL，或注入的空 env）→ **不共享**。不回落硬编码路径：注入的空 env 会因此静默写到真实机器的共享位置。
- **桶键就是 providerId**：一条 provider 配置 = 一份策略 = 一个桶，两端同名即共享。同一家供应商的不同 Key（中转站多账号）合用一个桶——要各算各的配额就多建一条 provider 配置，客户端不替你猜哪两把 Key 属于同一份配额。（此前按凭据哈希分桶，导致同一 provider 因端点写法/Key 存放方式不同而静默分裂成两个桶。）
- **公平性变弱**：账本说不出「谁先到」，两端同时醒来时谁抢到算谁的。跨进程 FIFO 要么做不到、要么得把排序状态也搬进文件，不划算——配额约束要的是节奏，不是先后。进程内仍严格 FIFO。
- **时钟偏差**：桶按「过了多久」补令牌。两端时钟不同步会让补算偏一点，方向不确定但有界（偏差秒数 × N/60000 个令牌，且被桶容量钳住）。负的时间差一律按「未经过」处理，绝不凭空造令牌。

### 并发读数：一人一份报告 + 收敛

**为什么不能照抄上面那套。** 令牌扣减是**瞬时**的：读→补→扣→写，锁持毫秒级就还，没有「归属」。并发
在飞数是**持续占用**的（几秒到几分钟），照抄就得回答「这个占用还有效吗」——把「谁持有槽」写进共享
文件，就必须配租约、心跳续期与崩溃回收；而槽的租约时长必须 ≥ 最长请求时长，睡眠/休眠又会把续约打停
（醒来发现自己的槽被判死偷走 → **超发**），且崩溃会**永久泄漏**槽位（计数只增不减，只能人工删文件）。
代价与风险都不成比例，所以**不做分布式信号量**。

改用**广告 + 收敛**：每个进程只写自己那一份报告（一人一文件、无锁），文件 mtime 就是「还活着」的证据；
另一端在自己要被挡住时（以及有在飞时的轮询节拍上）读一眼，用 `N − 别人` 压住自己的上限。

- **位置**：`%ProgramData%\zcode\provider-concurrency\`（WSL 侧 `/mnt/c/...`），与账本同一个锚点和开关。
- **一份报告一个人写**：文件名 `sha256(providerId)` 的前 16 位十六进制 + `.` + 实例 id + `.json`（providerId 只进内容——进文件名要跨 Windows/WSL 安全），内容 `{version, providerId, count}`。写用「临时文件 + rename」：读者看不到半截 JSON，顺带把 mtime 刷新了，所以**写报告同时就是报活**。
- **保活 1 秒 / 存活期 3 秒**：有在飞就至少每秒重写一次；超过 3 秒没更新的报告按「进程没了或睡了」
  处理并清掉。崩溃后另一端最多 3 秒收回它的份额——共享态里**没有可泄漏的东西**。
- **读的时机**：准入快路径只用「最后观察到的值」（同步、可能偏旧）；被挡住时先重读一次（别人已经放掉
  的不该排假队）；有在飞或有人排队时按 250ms 轮询（别人放行不会通知我们）。空转（没在飞、没人排队）
  一次 IO 都不做。
- **下限钳在 1**：`max(1, N − 别人)`。别人报满时不把自己卡成 0——否则缺口只能等对方放行，对方一卡就是
  互等。代价是边界上可能短暂到 `N + 1`。
- **收敛而非严格**：读数有刷新间隔，窗口内两端可能短暂超发，**最坏退到「各限各的」**（= 今天的行为），
  稳态收敛到 N。要的是「稳态不怼上游的墙」，不是毫秒级精确配额。
- **降级与时钟**：目录不可达/读不动一律按「别人占 0」算 → 退回进程内上限，一条 warn（60 秒节流）。
  判别人是否过期同样只用文件系统时钟；拿不到时钟就把候选**全额算成在用**（保守），而不是拿本端时钟瞎判。

### 所有权与不变式（RPM 账本）

- 余额的唯一所有者是那个文件；共享模式下进程内的桶**完全不参与**（只有降级时才接手）。
- 临界区只有「加锁 → 读 → 补 → 扣 → 写 → 放锁」，锁的持有时间在毫秒级。
- **抢锁必须是有限等待**（2 秒）：抢不到就降级，不能把模型请求挂在文件锁上。
- **判僵尸锁只看 mtime 年龄，不看 pid**：Windows 的进程号在 WSL 里毫无意义，按 pid 判活会把**活锁**当成僵尸偷走，于是两个进程同时进临界区。
- **判年龄必须用同一个时钟**：锁的 mtime 出自文件系统，而 WSL2 的内核时钟与 NTFS 时钟有漂移，拿本端时钟去减会让活锁被立刻判死。所以「现在」也取自文件系统——写一个探针文件、读它的 mtime（与锁在同一次挂载上，同一个时钟），减法与两端时钟差无关。只在锁已被占用时才付这个探针成本。
- 写是「同目录临时文件 + rename」，读者不会看到半截 JSON。

### 所有权与不变式（并发报告）

- 在飞数的唯一所有者仍是**本进程内**的治理器闸门；共享目录里只有「我此刻有几个在飞」的**广告**，不是一份配额账本——所以**永远不去解引用、不去改别人的报告**（读侧只按前缀匹配 + 排除自己那一份）。
- 一个进程一份报告（`provider-concurrency-shared` 的进程级单例）：一个进程里的多个 app（会话）共用同一份读数，否则另一端会把同一批请求数重复加。
- **没有任何需要回收的状态**：判活完全靠 mtime 年龄（1 秒保活、3 秒过期），进程崩了、被杀了、睡了，另一端最多 3 秒后就把它的份额收回来；过期报告顺手删掉，不留垃圾。
- **下限钳在 1**：可用额度是 `max(1, N − 别人)`，两侧都不许因对方报满而把自己卡成 0（那会变成互相等）。
- **空闲零开销**：没有在飞、也没有等待者时不写不读不排定时器；`maxConcurrent` 未配置的 provider 完全不碰这个目录。

### 失败语义（共享部分）

- **绝不 fail-open**：账本侧锁超时、目录不可写、内容损坏一律退回**进程内限速**（= 没有共享账本时的行为）；并发侧目录读不动一律按「别人占 0」算。两者都退到「本进程自己按配置卡」，而不是放开不管——反过来「读不到就不限速」会让一次挂载失败变成完全不限速。
- 降级记一条 warn 并按 60 秒节流，不刷屏；账本文件内容损坏按空账本继续（下一次写就修好），也记一条 warn。
- 账本降级期间进程内桶与共享账本**不叠加计数**：退化的那几次按进程内额度走，恢复后回到账本。极端抖动下总吞吐介于「纯共享」与「纯进程内」之间，有界。
- 并发侧拿不到文件系统时钟时**不猜**：候选报告全额算成在用（保守方向），宁可少放行也不多放行。

## 并发上限（provider 闸门）

- **声明语义**：`maxConcurrent` = 该 provider **总共**多少个在飞的模型请求，与模型无关。治理器按 providerId 一道闸结算所有模型桶的在飞总和（含 observer）；同机多端共享时，这个「总共」是**两端合起来的**（本进程只用 `N − 别人`，见上一节）。
- **AIMD 不动**：cap 的爬升/冷却/空闲重置仍长在 `${providerId}/${modelId}` 桶上。配置的上限只是把「能放行多少」从上面钳住——AIMD 学到的 cap 高于上限时，放行由 provider 闸门拦；上限高于 AIMD cap 时照旧。
- **主代理优先通道**：配置了上限的 provider 上，主代理与 legacy 子代理的请求排在优先队列；放行只需 provider 闸门放行（模型的 AIMD cap 与冷却不拦它）。run 的请求走 run 间轮转队列，且要**同时**过 AIMD 闸门与 provider 闸门。
- **跨模型桶唤醒**：任何一个模型桶的请求结算释放 provider 名额后，该 provider 的所有模型桶都尝试放行一轮等待者。
- **上限热更新**：每次准入重读配置。调大立刻放行、调小只拦新请求（在飞的自然结束，不抢占）；取消配置（`null` / 缺省）即恢复无闸门行为。
- **等待可观测**：主代理的请求因 provider 闸门排队时，runner 照常发 `model_request_queued` / `model_request_admitted`（reason `concurrency`）——快路径不命中是唯一依据，配置了上限才可能发生。

## 所有权与不变式

- 配置唯一来源：`ProviderConfig.requestPolicy`（稀疏语义：省略 = 继承，`null` = 清除；`requestsPerMinute` 1~600，`maxConcurrent` 1~128，均整数）。
- RPM 桶的唯一所有者：默认是 `createProviderRateLimiter` 的进程单例（按 `providerId` 分桶）；装配了共享账本时改为那个文件（键同为 providerId）。
- 并发在飞数的唯一所有者：`workflow-concurrency-governor` 的进程单例（AIMD 桶 + provider 闸门）；同机多端共享时，闸门的**可用额度**还要扣掉另一个进程广告的在飞数（那份读数归 `provider-concurrency-shared` 的进程单例，只读不写别人的报告）。
- 端口的唯一装配点：`create-app.ts` 的 `providerRateLimit` 与治理器单例的 resolver，其余位置只消费、不各自构造。
- **等待顺序是载荷性的**：`awaitRateLimit` 必须在抢并发槽**之前**（`admitAttempt` 固定先限速后 `tryAcquire`）。反了会形成「持槽者等令牌 → 令牌要等已发出的请求 → 别人在排队等槽」的三方互等死锁。
- 限速层只读自己的令牌桶，不碰任何并发槽；治理器只管并发槽，不读令牌桶。
- 准入端口的覆盖必须一站式：任何拿到端口的路径（含 legacy 子代理）都受限；再出现「并发直通」的旁路票，provider 闸门就会被绕开。

## 失败语义

- `requestsPerMinute` / `maxConcurrent` 非法（0 / 负数 / 非有限 / 越界由 schema 拒绝）等价于不启用——0 会让配额永远补不满（RPM）或并发永久为 0（并发），那是把所有请求永久挂起。
- 未启用策略的 provider 不建桶、不排定时器、不留状态；`awaitRateLimit` 返回 0，且不发等待事件（否则「真在等并发」这条信号会被淹掉）。
- 等待期间 abort：等待者立刻摘除并 `reject(signal.reason)`；队列空了连定时器一起撤，避免用户取消后进程被无主定时器拖住。
- 时钟回拨（系统改时间、NTP 校正）不凭空造令牌：负时间差按「未经过」处理。
- 限速器自身不抛错、不干预重试：真撞上 429 仍走既有指数退避。

## 迁移边界

- **桶键从凭据哈希改为 providerId**：同一 provider 配置的两端（Windows / WSL）从此必然同名共享；此前因 Key/端点表面差异而分裂的桶合并为一个。行为差异只在用户给同一 providerId 配了多个不同 Key 时可见——它们从此合用一份额度（互相限速）；要回到各算各的口径，多建几条 provider 配置。
- legacy 两条路径从「只限速、并发直通」改为「主代理同款 observer 端口」：配置了 `maxConcurrent` 时它们的请求会守 provider 总量、参与排队（等待事件 reason `concurrency` 出现在它们的时间线上）；未配置时并发行为逐字不变。
- 端口是可选的：未装配的调用方行为逐字不变（`admitAttempt` 在端口缺席时返回空实现）。
- **同机多端的并发上限从「各限各的」变成「合起来限一个 N」**：此前两端各按配置值卡自己（合计可能到 2N），现在可用额度是 `N − 对方广告的在飞数`。边界上（刷新窗口内）仍可能略超，**最坏退到旧行为**，稳态收敛到 N。这是**共享读数**而不是严格配额；要严格就得做分布式信号量（租约 + 心跳续期 + 崩溃回收 + 睡眠/休眠处理），取舍见「跨进程共享」。
- 已知缺口：限速等待只记一条日志，UI 上不显示「在等令牌 / 何时重试」；并发读数在纯 Linux / macOS 上不共享（不猜路径——多用户机器上猜错会让两个用户互相限流）。
